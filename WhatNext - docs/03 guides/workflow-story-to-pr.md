# Workflow: Story → Issue → Spec → Commit → PR

__Last Updated__: 2026-03-08
__Status__: Active

---

This guide describes WhatNext's end-to-end development workflow from the moment an idea surfaces to the moment it merges to `main`. It is the team's operational reference, not an aspirational document. If a step here doesn't match reality, update the guide.

---

## 1. Branching Strategy

### Branch Hierarchy

```ts
main
└── mvp            (active — ships to main when MVP is complete, then deleted)
└── dev            (created from main after MVP merges — day-to-day working branch)
    └── feature/…
    └── fix/…
    └── docs/…
    └── refactor/…
    └── agent/…    (optional prefix for Claude Code worktree branches)
```

__`main`__ — Always stable. Protected. Every commit here is a shippable state. No direct pushes. Merges arrive only via reviewed PRs.

__`mvp`__ (current) — Temporary convergence branch for the MVP milestone. Once the MVP PR merges to `main`, `mvp` is deleted. `dev` is then created from that clean `main` commit.

__`dev`__ (planned) — Created from `main` immediately after the MVP PR lands. The day-to-day working branch for all post-MVP development. Feature branches fork from here. All changes flow through `dev` before reaching `main` — including hotfixes.

__Feature / fix / docs / refactor branches__ — Short-lived, one logical unit of work. Branch from `dev` (or `mvp` while it exists). Delete after merge.

### Branch Naming Conventions

```ts
feature/<short-description>      # new capability
fix/<short-description>          # bug fix
refactor/<short-description>     # non-functional change
docs/<short-description>         # documentation only
agent/<short-description>        # Claude Code worktree (auto or manual)
worktree-agent-<hash>            # auto-generated by Claude Code (leave as-is)
```

- Lowercase, hyphens only
- Terse: `feature/session-persistence` not `feature/add-session-persistence-to-rxdb`
- One logical change per branch; if scope creeps, open a second branch

### Hotfix Strategy

All fixes flow through `dev` first. There is no shortcut directly to `main`.

```ts
fix/my-hotfix → PR to dev → merge → fast-forward main to match dev
```

If a critical fix is needed and `dev` has in-flight work, branch from `dev`, fix, PR to `dev`, then open a second PR from `dev` to `main` once the fix is isolated and verified.

### Worktrees (Agentic Parallel Work)

Claude Code uses `git worktree` to run multiple tasks in parallel without polluting the working directory. Worktree branches are auto-named `worktree-agent-<hash>`. Do not rename them. __Claude Code is responsible for cleaning up its own worktrees__ after every session:

```bash
git worktree remove <path>
git branch -d worktree-agent-<hash>
```

## 2. The Five-Stage Flow

```ts
Story → Issue → Spec → Commits → PR
  (why)  (what)  (how)  (work)  (review + merge)
```

Each stage has an artifact, an owner, and a definition of done.

---

## Stage 1: Story

### What It Is

A narrative that captures user value, the user, and the motivation. Stories are the "why." Non-technical by design — no implementation details.

Minimum format:

> "I want to [do something] so that [I get this value]."

Stories may also be richer narratives (see [[the-walled-garden-cracks]]), but the sentence above is the minimum signal.

### Who Creates It

Human — the product owner or any contributor with a clear user insight. Claude Code can help articulate or refine, but should not originate stories.

### Where It Lives

Every story lives in `docs_md/07 stories/` as a standalone document, regardless of size. Even a one-sentence story gets a file. This keeps Obsidian's linking and graph intact and builds a comprehensive record of the project's evolution.

__Filename__: `story-<slug>.md`

```yaml
---
tags:
  - stories/<category>
date created: <date>
relates to: "[[whtnxt-nextspec]]"
---
```

Link to the story doc from the GitHub Issue body using its WikiLink: `[[story-<slug>]]`.

### Definition of Done

- Human desire clearly stated in one or two sentences
- Clear who the user is (end user, coordinator, participant)
- Decoupled from implementation — describes the outcome, not the mechanism
- File exists in `docs_md/07 stories/`

---

## Stage 2: Issue

### What It Is

A GitHub Issue that translates the story into trackable work with acceptance criteria. Issues are the "what."

Issues are intentionally slim. Rich context lives in the story doc and spec; the issue is the actionable unit.

### Who Creates It

Human, or human-reviewed if drafted by AI. No issue should be opened without a human approving the acceptance criteria.

### Issue Template

Use the existing `TODO` template (`.github/ISSUE_TEMPLATE/todo.md`) for feature work and `bug_report.md` for defects.

Minimum fields:

```markdown
### Story

[[story-<slug>]]

### Description

What needs to be built. Two to five sentences, no implementation detail.

### Acceptance Criteria

- [ ] Observable outcome (not a code task)
- [ ] …

### Scope Notes (Optional)

What is explicitly out of scope.

### Related

- Blocked by: #<issue>
- Blocks: #<issue>
- Related concepts: [[Concept-Name]]
```

### Labels

| Label | Meaning |
|---|---|
| `bug` | Defect against expected behaviour |
| `blocked` | Cannot proceed — dependency or decision outstanding |
| `needs-spec` | Open but spec not yet written |
| `needs-story` | Open but story doc not yet written |
| `good-first-issue` | Small, well-scoped, appropriate for a new contributor |

> Note: Work is not labelled based on whether it was generated by an agent or a human. All PRs are human-owned (see §3).

### GitHub Projects Board

All issues are tracked on the [WhatNext GitHub Projects board](https://github.com/users/mads-jm/projects/2). Assign issues to the board and move them through columns as work progresses.

### Definition of Done

- Assigned to a milestone
- At least one acceptance criterion
- Story doc linked
- If complex: `needs-spec` label applied and Stage 3 triggered
- Human has reviewed and approved

---

## Stage 3: Spec

### What It Is

A technical specification describing how the acceptance criteria will be met — data model changes, interface contracts, component architecture, IPC changes, migration requirements. The spec is the "how."

Not every issue needs a spec. Use judgment:

- Simple UI fix → no spec, work directly
- New DB field → brief spec note in the issue comment is fine, but document in `docs_md/` if it introduces a pattern
- New subsystem, provider interface, or cross-cutting change → full spec in `docs_md/04 architecture/`

All specs eventually land in `docs_md/` for Obsidian graph visibility. Issue comments are acceptable for quick drafts, but the final spec belongs in the vault.

### Who Creates It

Human or human + Claude Code collaboratively. The human must review and approve before implementation begins.

### Where It Lives

| Scope | Location |
|---|---|
| Architectural decision | `docs_md/04 architecture/adr/adr-YYMMDD-<slug>.md` |
| Feature / component spec | `docs_md/08 specs/<feature-slug>.md` |
| Quick spec draft | GitHub Issue comment (migrated to `docs_md/08 specs/` before implementation) |

For ADRs, follow the template in [[ADR]] and the established format in `docs_md/04 architecture/adr/`.

### Spec Minimum Content

```markdown
## Context
What situation prompted this work?

## Interface / API Contract
What do callers see? (TypeScript interfaces, IPC channel names, hook signatures)

## Data Model Changes
Schema version bumps, new fields, migrations required

## Sequence / Flow
Step-by-step description of the happy path

## Error Cases
What can go wrong and how it is handled

## Out of Scope
What this spec explicitly does not cover

## Open Questions
Decisions that must be made before implementation begins
```

### Definition of Done

- All open questions resolved
- Schema changes documented with migration plan
- Human has explicitly approved (GitHub comment or PR review)
- `needs-spec` label removed from the issue
- Spec is in `docs_md/`

## Stage 4: Commits

### What Commits Are

Individual save points during implementation. Each commit should be a coherent unit of change — not necessarily a complete feature, but a state that compiles and makes sense on its own.

### Commit Message Convention

WhatNext uses __Conventional Commits__ with a rich body:

```ts
<type>(<scope>): <short summary, ≤72 chars>

[Optional body: one or two sentences of context — the "why", not the "what".]
```

__Types__: `feat`, `fix`, `refactor`, `docs`, `chore`, `test`, `style`, `perf`

__Scope__: the area of the codebase touched — e.g., `sessions`, `p2p`, `spotify`, `db`, `ipc`, `ui`, `auth`

__Summary__: imperative mood, sentence case, no period — `Add session persistence` not `Added session persistence.`

__Examples__:

```ts
feat(sessions): Add provider abstraction for TrackSource and PlaybackProvider

Decouples session logic from Spotify-specific implementation so that
future sources (ManualTrackSource, P2PTrackSource) can be swapped in
without changing session orchestration.
```

```ts
fix(db): Correct schema migration for trackSchema v0→v1

albumArtUrl and albumArtLocalPath were not being populated for tracks
imported before the artwork caching feature landed.
```

```ts
docs(workflow): Add Story→Issue→Spec→Commit→PR guide
```

### Attribution for AI-Assisted Work

When Claude Code contributes to a commit, __do not include a `Co-Authored-By` line in the commit itself__. Instead, acknowledge AI assistance in the PR description. This keeps the commit log clean and reinforces human ownership of every commit. Release notes generated from PRs can credit AI tooling where relevant.

### What to Commit

- Compilable states where possible
- No commented-out blocks of old code — remove them or open a follow-up issue
- No `.env` files, credentials, or secrets — ever
- Stage specific files by name, not `git add .` blindly

### Quality Before Pushing

```bash
cd app && npm run typecheck   # must pass (pre-existing exempt errors in TODO.md are grandfathered)
cd app && npm run lint        # must pass
```

When the CI pipeline is live, it will also run `react-doctor`. Run it locally if working on React components.

## Stage 5: Pull Request

### What a PR Is

A PR is a request for review and merge. It is the last quality checkpoint before work becomes permanent.

__Every PR is human-owned.__ Regardless of whether implementation was done with AI assistance, the person opening the PR is responsible for every line of code in the diff. There is no such thing as an "agentic PR" — there are only PRs, all subject to the same standards.

__No PR merges to `dev` or `main` without a human reviewer who is not the PR author.__ For `mvp` during rapid MVP development, self-merge is permissible for low-risk changes — document the exception in the PR body. Agents cannot merge to `main` or `dev` under any circumstances.

### PR Template

`.github/PULL_REQUEST_TEMPLATE.md`:

```markdown
### Summary

One to three sentences. What changed and why.
Reference the Conventional Commit type: feat / fix / refactor / docs / chore.

### Related

Closes #<issue-number>
Story: [[story-<slug>]]

### Type of Change

- [ ] New feature (`feat`)
- [ ] Bug fix (`fix`)
- [ ] Refactor / cleanup (`refactor`)
- [ ] Documentation (`docs`)
- [ ] Chore / tooling (`chore`)

### Checklist

- [ ] `npm run typecheck` passes
- [ ] `npm run lint` passes
- [ ] Acceptance criteria from the linked issue are met
- [ ] New or changed behaviour is manually tested
- [ ] Documentation updated if applicable (concept pages, CLAUDE.md, ADR)
- [ ] No secrets or credentials in diff
- [ ] Squash commit message is rich enough to serve as a changelog entry

### AI Assistance

If Claude Code contributed to this PR, note it here:
e.g. "Implemented with Claude Sonnet 4.6 via Claude Code CLI."

### Screenshots (if UI changes)

### Notes for Reviewer
```

### Review Requirements

- __`dev` and `main`__: Always require at least one approving review from someone other than the PR author. No exceptions.
- __`mvp`__: One review recommended. Self-merge permissible for low-risk changes — note the exception in the PR body.
- __Any PR with P2P protocol changes__: Requires explicit human approval regardless of branch. See §3.

When reviewing a PR that used AI assistance, read the diff assuming the AI may have made locally-coherent but globally-wrong decisions. Verify intent, not just compilation.

### Merge Strategy

- __Squash merge__ by default — keeps `main`/`dev` history clean and readable as a changelog. Write a rich squash commit message; this becomes the release note.
- __Merge commit__ for significant milestones where the sub-commit history has narrative value (e.g., the MVP PR itself). Say so in the PR.
- __Never force-push to `main`.__

### Closing Issues

Use `Closes #<n>` in the PR body so GitHub auto-closes the issue on merge. Prefer one-to-one PR-to-issue; only close multiple issues in one PR if the work is genuinely coupled.

## 3. Agentic Work Conventions

### Principle: Human Ownership

Code is code. There is no distinction between "agentic" and "human" work in the PR label, review process, or merge gate. What matters is that a human reviews and owns every change before it merges.

Claude Code assists in two patterns:

1. __Inline assistance__ — human drives, Claude edits/suggests. Human commits and opens PR.
2. __Autonomous task__ — Claude takes an issue, opens a worktree branch, implements, and prepares a PR for human review. Human reviews, refines if needed, and merges.

In both cases: the human is the author of record for the PR.

### Scope Gates

__The P2P protocol is off-limits for fully autonomous agentic work__ without explicit human approval. This covers:

- `app/src/main/p2p/` and any libp2p stream handlers
- `app/src/renderer/db/replication*.ts`
- The handshake protocol (`app/src/main/handshake.ts`)
- Any changes to `app/src/shared/core/ipc-protocol.ts` that affect P2P message types

Everything else may be implemented autonomously, subject to normal review.

### Staging for Agentic Work

If agentic output outpaces human review capacity, use intermediate staging branches above `dev`:

```ts
agent/feature-x  →  (human reviews, approves, merges)  →  dev
```

Do not accumulate unreviewed agentic PRs against `dev` or `main`.

### Worktree Cleanup

After a worktree-based branch is merged, Claude Code cleans up immediately in the same session:

```bash
git worktree remove <path>
git branch -d worktree-agent-<hash>
```

## 4. Quality Gates

### Before Any Push

```bash
cd app && npm run typecheck
cd app && npm run lint
```

Both must pass. The pre-existing typecheck errors in `TODO.md` (libp2p stream API mismatches, Vite moduleResolution) are grandfathered — do not introduce new errors.

### Before Merging to `dev` or `main`

- All PR checklist items checked
- Linked issue acceptance criteria verified manually
- No unresolved review comments
- Branch is up to date with target branch

### CI Pipeline (Planned)

Once the CI pipeline exists (`.github/workflows/ci.yml`), every PR will automatically run:

```ts
typecheck → lint → react-doctor
```

These must pass before merge. Electron packaging runs on merge to `main` (not on every PR).

### Branch Protection Rules (to Be Configured on GitHub)

__`main`__:
- Require PR before merging
- Require at least 1 approving review
- Dismiss stale reviews on new commits
- Require CI status checks to pass
- No force pushes
- No deletions

__`dev`__ (once created):
- Require PR before merging
- Require at least 1 approving review

## 6. Milestones and Versioning

### Current Milestones

| Milestone | Description |
|---|---|
| MVP (`v0.1.0`) | Collaborative Playlist Sessions — coordinator model, P2P join, Spotify import |
| Phase 2 (`v0.x.0`) | Active management, additional import adapters, True Collaborate mode |
| Phase 3 (`v1.0.0`) | Sovereign music platform — stable P2P protocol, feature-complete |

See [[whtnxt-nextspec]] and [[the-walled-garden-cracks]] for milestone scope.

### Versioning Scheme

```ts
0.0.x   Incremental feature additions and development builds
0.x.0   Significant milestones (e.g., MVP, major feature complete)
x.0.0   Major milestones — stable P2P protocol, feature-complete, defining change
```

`v1.0.0` ships when the P2P protocol is stable and the implementation meets all FC goals.

### Releases and Changelog

Releases are automated via __semantic-release__, triggered on merge to `main`. Release notes are generated from squash commit messages — this is why rich squash messages matter.

For major releases (e.g., `v1.0.0`), supplement the automated notes with a hand-written release announcement.

## 7. Quick Reference

```ts
New idea
  └─> Write story doc (docs_md/07 stories/story-<slug>.md)
        └─> Open GitHub Issue (todo template, link story, acceptance criteria, labels)
              └─> If complex: write spec (ADR or architecture doc in docs_md/)
                    └─> Branch from dev/mvp
                          └─> Implement → commit (typecheck + lint before push)
                                └─> Open PR (closes #issue, checklist, human review)
                                      └─> Squash merge → delete branch → issue auto-closes
                                            └─> semantic-release generates GitHub Release
```
